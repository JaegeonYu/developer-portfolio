대규모 운영 데이터 정리

emroCloud · 로그 / 메일 발송 이력

Oracle Standard Edition SQL ROWID Batch Delete

Archive Log 증가를 확인하고, ROWID 기반 삭제의 배치 건수를 더 작게 제한했습니다.

문제 해결 과정

보존기간 조건만으로 대량 DELETE를 실행하던 방식에서, Archive Log 증가를 확인하고 삭제 건수와 트랜잭션 크기를 명시적으로 제한하는 방식으로 바꿨습니다.

AS-IS · 기간 조건에 해당하는 데이터를 일괄 삭제

로그와 메일 발송 이력 등 보존기간이 지난 데이터를 정리하는 작업이었습니다. 약 2억 건 규모의 정리 대상을 분석했으며, 날짜 조건만 있는 DELETE는 한 번의 작업이 처리할 건수를 명확히 제한하지 못했습니다.

운영 중 확인한 문제 · 삭제에도 로그 공간이 필요

데이터를 삭제하는 작업에서도 변경 내용에 대한 Redo가 발생하고, Archive Log가 쌓여 용량이 급증하는 점을 확인했습니다. 삭제 대상의 용량뿐 아니라 작업이 새로 발생시키는 로그 공간도 고려해야 했습니다.

한 번의 처리 분량을 더 작게 조정하고, 스크립트에서 처리 건수를 명확히 제한하는 방향으로 변경했습니다.

TO-BE · ROWID 커서와 건수 제한으로 작업 분할

  1. 보존기간을 지난 대상의 ROWID 조회

    날짜 조건은 유지하고, 커서가 삭제할 행의 ROWID를 가져오도록 구성했습니다.

  2. 일정 건수만 FETCH하고 해당 ROWID 삭제

    한 번에 가져오는 건수를 제한하고, 이번 묶음의 ROWID만 DELETE 대상으로 사용했습니다. 전체 대상 건수와 한 번의 처리 건수를 구분했습니다.

  3. 일정 건수마다 COMMIT 후 다음 묶음 처리

    대상 전체를 하나의 큰 트랜잭션으로 처리하지 않고 작업을 나눴습니다. Archive Log 증가를 확인한 뒤 배치 분량을 더 타이트하게 줄여 처리 단위를 조정했습니다.

개선의 의미와 한계

배치별 삭제 건수와 트랜잭션 크기를 제어할 수 있도록 바꿨습니다. 작은 배치와 COMMIT이 같은 데이터를 삭제할 때 발생하는 전체 Redo·Archive Log 양을 없애거나 자동으로 줄여 주는 것은 아닙니다. 작업 단위를 줄이는 것과 누적 로그 공간을 확보하는 것은 함께 고려해야 할 문제입니다.

SQLP 학습으로 넓힌 관점 · Enterprise Edition이라면?

실제 운영 DB는 Oracle Standard Edition이었기 때문에, 이번 정리에는 ROWID 기반 분할 DELETE를 적용했습니다. 이후 SQLP를 공부하며 배운 파티셔닝을 바탕으로 “Enterprise Edition 환경이라면 어떻게 접근할 수 있을까?”라는 대안도 고려했습니다.

날짜 기준 파티션을 구성할 수 있고 보존기간 경계와 파티션 경계가 맞는다면, 행별 DELETE를 반복하는 대신 오래된 파티션을 DROP하는 방식으로 보존기간 관리를 바꿀 수 있습니다. 파티션 방식은 실제 운영에 적용한 결과가 아니라 학습 내용을 실무 문제에 연결해 검토한 접근입니다.
