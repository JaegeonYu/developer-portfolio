대규모 운영 데이터 정리

emroCloud · 7년간 누적된 서비스 로그 데이터 삭제 · 약 2억 건 규모의 정리 대상 분석

문제 상황

7년간 쌓인 서비스 로그 중 보존기간이 지난 데이터를 삭제하는 작업이었습니다. 개발환경까지는 날짜 조건으로 일괄 DELETE하는 방식으로 작업했습니다. 이 과정에서 DELETE가 발생시키는 Redo와 Archive Log로 로그 공간이 급격히 늘어나는 것을 확인하고, 운영환경 작업에서는 처리 분량과 트랜잭션 크기를 제어하도록 방식을 바꿨습니다.

AS-IS · 개발환경까지의 작업

개발환경에서는 날짜 조건만 있는 DELETE로 보존기간이 지난 데이터를 일괄 처리했습니다. 한 번의 삭제 건수와 트랜잭션 크기를 명확히 제한하지 않은 방식이었습니다.

TO-BE · 운영환경 작업

운영환경에서는 커서로 대상 ROWID를 조회하고 건수를 제한해 FETCH한 뒤 해당 묶음만 DELETE했습니다. 일정 건수마다 COMMIT하며 다음 묶음으로 진행하고, 로그 증가를 고려해 배치 크기를 조정했습니다.

운영환경 적용 · 삭제 처리 단위를 분할

보존기간 조건으로 대상 ROWID 조회날짜 조건 유지
↓
건수를 제한해 FETCH → 해당 ROWID DELETE전체 대상과 1회 처리 분량 분리
↓
일정 건수마다 COMMIT → 다음 묶음 반복Archive Log 증가를 확인하며 배치 분량 조정

판단과 해결

기존 운영 테이블에서 실행할 수 있는 ROWID 기반 분할 삭제를 적용해 배치별 작업량과 트랜잭션 크기를 제어했습니다. 작은 배치와 COMMIT이 전체 Redo·Archive Log 양 자체를 자동으로 줄이는 것은 아니므로, 작업 단위와 누적 로그 공간을 함께 고려했습니다.

SQLP 학습으로 넓힌 관점 · 날짜 파티션

실제 적용은 Standard Edition의 분할 DELETE입니다. 이후 학습을 통해 보존기간과 경계가 맞는 날짜 파티션이라면 오래된 파티션을 DROP하는 대안도 검토했습니다. 실제 적용 결과가 아니며, 도입 시 기능·사용 권한과 기존 테이블 전환, 인덱스·참조 제약 영향을 확인해야 합니다.
