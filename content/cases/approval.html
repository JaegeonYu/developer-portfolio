01 / 낙관적 동시성 제어

일괄결재 처리 안정성 개선

2025.09 — 2025.11 · emroCloud · 상태 기반 대상 제외

개별 결재 처리 중 동일한 건이 재요청되는 상황에 상태 기반 제어를 적용했습니다. 처리중인 건의 재진입을 구분하고, 완료된 건도 재실행 대상에서 제외하도록 개선했습니다.

AS-IS · 개별 결재 처리 중 동일 건 재요청

일괄결재는 선택한 개별 결재 건마다 업무 모듈을 실행하는 방식이었습니다. 선행 트랜잭션이 아직 완료되지 않았는데 사용자가 같은 결재 건을 다시 요청하면, 후행 요청도 해당 건의 결재를 진행하면서 업무 모듈의 데이터 정합성이 맞지 않는 문제가 발생했습니다.

변경 전 · 선행 트랜잭션 종료 전 동일 결재 재요청

사용자가 일괄결재 실행
↓
선택한 개별 결재의 업무 모듈 실행 선행 트랜잭션에서 결재 처리 진행
↓
선행 트랜잭션이 완료되기 전 동일 건 재요청 후행 요청에서도 같은 결재의 업무 모듈 실행
↓
동일 결재의 업무 처리가 중복 진행 업무 모듈의 데이터 정합성 오류 발생
문제의 핵심 · 처리중인 동일 결재의 재진입

선행 트랜잭션이 끝나지 않은 동안 동일한 결재가 다시 실행될 수 있다는 점이 문제였습니다. 요청이 들어온 시점에 해당 결재가 처리중인지 구분하고, 이미 처리중이거나 완료된 건은 재실행 대상에서 제외할 필요가 있었습니다.

낙관적 동시성 제어를 적용해 ‘결재상태’ 컬럼을 기준으로 처리 대상을 구분했습니다. 이미 일괄결재처리중이거나 완료된 건은 재실행 대상에서 제외하고, 실제 건별 처리는 별도 신규 트랜잭션으로 분리했습니다.

TO-BE · 시작 상태 기록 → 건별 처리 → 조건부 완료
  1. 시작 상태를 기록하는 트랜잭션

    일괄결재 시작 시 이미 ‘일괄결재처리중’이거나 ‘결재완료’인 건은 제외하고, 나머지 대상의 상태를 ‘일괄결재처리중’으로 변경합니다. 재요청이 처리중·완료 상태를 다시 덮어쓰지 않도록 했습니다.

    트랜잭션 1 · 재실행 대상 구분

    일괄결재 시작 · 결재 ID 목록 전달
    ↓
    현재 결재상태 확인 처리중이거나 완료된 건인가?
    ↓
    처리중 또는 완료
    이번 처리 대상에서 제외 재요청으로 해당 상태를 덮어쓰지 않음
    그 외 처리 대상
    일괄결재처리중으로 상태 변경 시작 상태를 기록하는 트랜잭션
  2. 결재 건마다 신규 트랜잭션으로 처리

    건별 전처리 모듈을 실행한 후, 해당 결재 ID의 현재 상태가 ‘일괄결재처리중’인 경우에만 완료 상태로 갱신합니다. 시작 상태 변경과 개별 결재 처리의 트랜잭션 경계를 분리했습니다.

    결재 한 건의 신규 트랜잭션 시작 requirednew = true
    ↓

    ↓
    해당 ID의 상태가 일괄결재처리중인가? 완료 전환의 상태 조건 확인

    완료 상태를 갱신하지 않음 상태 조건에 맞는 행만 변경

제공된 구현 흐름을 처리 단계와 상태 분기로 정리한 도식입니다.

개선한 점

처리중·완료 건을 재요청 대상에서 제외하고, 일괄결재의 시작과 완료를 서로 다른 상태로 표현했습니다. 실제 처리 단위는 건별 신규 트랜잭션으로 분리했습니다. 완료 갱신에는 현재 상태 조건을 추가해 의도한 단계의 결재만 완료로 전환하도록 했습니다.

02 / 비관적 동시성 제어

중복 입찰 제출 방지

다중 애플리케이션 서버 · 단일 DB

문제 · 검사는 있었지만 미커밋 제출을 감지하지 못함

공급사가 동일한 입찰에 제출한 뒤, 선행 트랜잭션이 끝나기 전에 네트워크 지연·오류로 요청을 다시 보냈습니다. 서비스에는 이미 제출 여부를 확인하는 로직이 있었지만, 후행 요청이 들어온 시점에는 선행 제출이 커밋되지 않아 기존 제출을 확인하지 못했고 두 번째 요청도 받아들여졌습니다.

그 결과 동일 공급사의 입찰 제출 데이터가 중복 생성됐습니다. 입찰 마감 이후 구매담당자가 조회할 때 한 건을 기대한 조회에서 여러 건이 반환되면서 오류가 발생했습니다. 검증 로직의 유무보다 검증과 커밋 사이의 경합을 다뤄야 하는 문제였습니다.

첫 요청의 제출 여부 확인제출 처리 중 · 아직 커밋 전 네트워크 지연으로 재요청선행 제출을 확인하지 못함 두 요청 모두 제출 처리중복 데이터로 조회 오류 발생
해결 · 기존 검증 앞에 입찰 행 잠금 추가

여러 서버가 하나의 DB를 공유하는 구조에 맞춰, 공급사 입찰 제출 로직의 시작점에서 SELECT … FOR UPDATE로 해당 입찰 행에 잠금을 걸었습니다. 서버가 달라도 같은 DB 행의 잠금을 기준으로 제출 흐름을 직렬화하는 비관적 동시성 제어를 적용했습니다.

입찰 제출 · 잠금 이후 기존 검증 실행

공급사의 입찰 제출 요청 여러 애플리케이션 서버 → 하나의 DB
↓
해당 입찰 행의 잠금 획득 입찰 ID 기준 SELECT … FOR UPDATE
↓
선행 트랜잭션이 있으면 잠금 대기 선행 커밋·롤백 후 잠금을 얻어 다음 단계 진행
↓
기존 서비스의 제출 여부 확인 선행 제출 결과를 반영해 같은 공급사의 제출을 판단
↓
이미 제출됨
중복 저장 차단 기존 서비스의 검증 로직 활용
제출 가능
입찰 제출 데이터 저장
↓
트랜잭션 커밋 · 잠금 해제 다음 요청이 잠금을 획득해 검증 시작
TO-BE · 잠금 획득 → 제출 여부 확인 → 저장
  1. 입찰 행의 잠금을 먼저 획득

    후행 요청은 선행 트랜잭션이 같은 입찰 행의 잠금을 유지하는 동안 제출 검증 단계로 넘어가지 못하고 대기합니다.

  2. 선행 트랜잭션 종료 후 기존 제출 여부 검사

    선행 트랜잭션이 커밋 또는 롤백해 잠금을 해제하면, 후행 요청이 잠금을 획득한 뒤 기존 서비스의 제출 여부 검사를 수행합니다. 앞선 제출이 커밋됐다면 이미 제출된 것으로 판단해 중복 저장을 막습니다.

  3. 제출 가능한 경우에만 저장 후 트랜잭션 종료

    검증과 제출 처리를 같은 트랜잭션 경계에 두고, 검증이 끝나기 전에 다른 제출 흐름이 끼어들지 않도록 순서를 제어했습니다.

개선한 점 · 기존 검증이 유효하게 동작하도록 실행 순서 보장

새로운 중복 검사만 추가한 것이 아니라, 검사와 저장이 동시에 진행되던 경로를 직렬화했습니다. 선행 제출 결과를 반영한 상태에서 후행 요청을 판단하도록 만들어 기존 서비스의 제출 여부 검사가 의도한 역할을 하도록 개선했습니다.

잠금 기준은 공급사별 행이 아닌 ‘입찰 ID의 행’입니다. 같은 입찰에 대한 여러 공급사의 제출도 이 잠금 지점에서 대기할 수 있으며, 모든 일반 조회를 막는 방식은 아닙니다.

두 사례에서 제어 지점을 나눈 기준

사례 제어 기준 적용 방식
