01 / 낙관적 동시성 제어

결재상태 컬럼을 이용한 일괄결재 재요청 제어

2025.09 — 2025.11 · 상태 기반 대상 제외 · 건별 트랜잭션

문제 상황

선택한 결재 건마다 업무 모듈을 실행하는 일괄결재에서, 선행 트랜잭션이 끝나기 전에 같은 건이 재요청됐습니다. 후행 요청도 해당 건의 업무 모듈을 실행하면서 중복 처리로 데이터 정합성이 어긋났습니다.

핵심 판단: 동일 결재의 재진입을 구분하려면 요청 도착 여부보다 현재 결재상태를 기준으로 처리 대상을 정해야 했습니다.

AS-IS

처리 중인 동일 결재가 다시 요청되면 후행 요청에서도 업무 모듈을 실행했습니다.

동일 결재의 중복 실행

선행 요청의 업무 모듈 실행트랜잭션 처리 중
↓
동일 결재 재요청선행 트랜잭션 완료 전
↓
같은 업무 모듈 중복 실행데이터 정합성 오류
TO-BE

‘결재상태’ 컬럼으로 이미 처리중·완료인 건을 제외하고, 처리 가능한 건만 ‘일괄결재처리중’으로 변경합니다.

상태 기준으로 실행 대상을 구분

시작 상태 변경처리중·완료 건은 제외
↓
건별 신규 트랜잭션에서 전처리시작 상태 기록과 실제 처리 경계 분리
↓
현재 처리중인 해당 건만 완료 갱신결재 ID + 결재상태 조건
내가 바꾼 점

시작 상태를 기록하는 트랜잭션과 실제 건별 처리를 분리했습니다. 시작 UPDATE에는 처리중·완료 제외 조건을, 완료 UPDATE에는 결재 ID와 현재 처리중 상태 조건을 두어 상태에 맞는 대상만 다음 단계로 전환하도록 했습니다.

02 / 비관적 동시성 제어

중복 입찰 제출 요청 직렬화

다중 애플리케이션 서버 : 단일 DB · 기존 서비스 유효성 검사 유지

문제 상황

서비스에는 이미 제출 여부를 확인하는 로직이 있었습니다. 하지만 네트워크 지연·오류로 재요청이 들어왔을 때 선행 제출이 아직 커밋되지 않아, 후행 요청도 미제출로 판단해 중복 저장했습니다. 이후 한 건을 기대한 조회에서 여러 건이 반환되며 오류가 발생했습니다.

핵심 판단: 여러 서버가 하나의 DB를 공유하므로, 기존 유효성 검사 전에 DB 행 잠금을 획득하도록 해 검증과 저장 흐름을 직렬화했습니다.

AS-IS

서버가 달라도 각 요청이 검사와 저장을 동시에 진행할 수 있었습니다. 유효성 로직은 존재했지만 미커밋 제출을 보지 못했습니다.

검사와 커밋 사이의 경합

서버 A: 제출 여부 검사 → 저장 중아직 커밋 전
↓
서버 B: 재요청의 제출 여부 검사선행 제출이 보이지 않아 미제출 판단
↓
두 요청 모두 제출 데이터 저장중복 데이터 생성
TO-BE

제출 상태를 검사하는 기존 서비스 로직 앞에 SELECT … FOR UPDATE를 추가했습니다. 같은 입찰 행의 잠금을 얻은 요청만 검증 단계로 진행합니다.

잠금 → 기존 검증 → 저장

서버 A / B → 단일 DB 입찰 행 잠금입찰 ID 기준 SELECT … FOR UPDATE
↓
선행 트랜잭션 종료 후 잠금 획득후행 요청은 잠금 지점에서 대기
↓
기존 서비스의 제출 상태 검사이미 제출했다면 중복 저장 차단
↓
제출 가능한 경우 저장·커밋트랜잭션 종료 시 잠금 해제
내가 바꾼 점

새로운 중복 검사로 대체하기보다, 기존 검사가 선행 제출 결과를 반영한 뒤 실행되도록 순서를 보장했습니다. 유효성 검사와 저장을 같은 트랜잭션에 두어 여러 서버의 요청이 DB의 동일한 잠금 기준을 따르게 했습니다.

잠금 기준은 공급사별 행이 아닌 입찰 ID의 행입니다. 같은 입찰의 다른 공급사 제출도 이 지점에서 대기할 수 있습니다.
