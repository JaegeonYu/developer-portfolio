스터디원 2명이 사용하는 SQL 튜닝 실습·자동 채점 시스템을 설계하고 운영했습니다. 결과 일치·Buffers 채점과 Hint Report 피드백으로 학습 의도와 실제 실행을 함께 확인합니다.

배경과 설계 조건

SQLP 취득 후 스터디원 두 명과 튜닝 스터디를 시작하며 멘토를 맡았습니다. 매주 문제를 공개하고 풀이를 확인하는 반복 작업을 줄이기 위해 운영 시스템을 만들었습니다. 브라우저만으로 참여할 수 있고, 운영비 0원을 목표로 하며, 제출 SQL·정답은 비공개로 유지하는 것을 조건으로 정했습니다.

주차 시작 시 문제, 개인별 할 일 목록과 포스팅 초안 PR을 자동 생성합니다. 멘토가 글을 리뷰·머지하면 사이트를 갱신하고 진행률을 다시 계산합니다. 공개 저장소는 별도 GitHub App으로 비공개 저장소에 재계산을 요청합니다.

DB는 데이터 소유 STUDY, 제출 SQL을 실행하는 읽기 전용 GRADER_RUN, 실행 통계를 조회하는 GRADER_STATS로 권한을 분리했습니다. 공개 데이터는 닉네임으로 표시하고, 배포 전 공개 금지 항목이 포함되면 빌드를 멈추도록 했습니다.

채점 기준: 실행 시간보다 데이터 접근량

같은 SQL도 캐시와 DB 부하에 따라 실행 시간이 달라져, 결과 일치와 읽은 블록 수(Buffers)를 기준으로 변경했습니다. 실행 시간은 장시간 SQL을 중단하는 제한으로만 남겼습니다.

로컬 Docker Oracle에서 10블록이던 SQL이 클라우드에서는 19블록으로 측정돼 목표값을 실제 채점 DB에서 다시 잡았습니다. 권한·네트워크·동시 제출도 클라우드에서 확인한 뒤 운영을 시작했습니다.

Hint Report로 의도와 실제 실행계획 확인

잘못 작성한 FULL 힌트가 무시됐는데도 다른 실행계획으로 목표를 만족해 통과한 사례가 있었습니다. 학습자가 의도한 방식과 실제 실행이 다른 문제를 드러내기 위해 Hint Report를 확인하고, 무시된 힌트를 댓글로 안내하며 해당 제출을 반려하도록 바꿨습니다.

Hint Report: E - FULL(e employees_dept_ix) ← Syntax error
